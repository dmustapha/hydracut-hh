# Lessons

- Lead hackathon intel with a plain-English explanation of the event and what participants actually build before presenting dense specification tables.
- Treat snapshot consistency and historical time travel as different capabilities. Verify current OSS query semantics before using temporal language in an idea.
- A generic supply-chain blast-radius graph is crowded. Differentiate through a verified HydraDB-native primitive and a narrower incident outcome.
# Lessons

## 2026-08-18: Never blur demo fixtures with user scans

- A security product must never imply that it seeds vulnerabilities into user projects to manufacture findings.
- User scans are read-only and every finding must be traceable to an exact imported dependency plus a real advisory or documented incident source.
- Say "all matching paths within the imported graph and declared bounds," not "complete impact," because dependency presence does not prove runtime exploitability or production compromise.
- Demo fixtures containing real historical vulnerable versions must be explicitly labeled and kept separate from unmodified user-project analysis.

## 2026-08-18: Never claim build readiness before the graph query and corpus are proven

- The self-hosted HydraDB OSS engine is the product computation layer; the hosted SDK cannot substitute for explicit Cypher and native path execution.
- Illustrative portfolio counts must never appear as product facts. Applications, paths, owners, and remediation candidates must be derived from the frozen authentic corpus.
- A historical public repository strategy still needs an honest portfolio model. Prefer real workspaces/CODEOWNERS or multiple clearly labelled repositories rather than fabricating internal teams.
- Do not call HydraCut ready until the published Docker image round-trips the exact `MSpaths` query and real candidate version transitions can be resolved and re-queried.

## 2026-08-18: Discovery precedes forge

- Do not interpret a request for complete scope validation as authorization to begin hackathon-forge.
- Finish a pre-forge scope document first: exact product behavior, authentic data corpus, verified database/runtime contracts, caveat ledger, boundaries, failure states, and proof plan.
- Forge begins only after the user approves that product definition.

## 2026-08-18: Preserve the combined winner, not only its prerequisite

- The selected direction is CampaignRadius plus HydraCut. CampaignRadius computes and proves the real exposure paths; HydraCut turns those paths into a bounded intervention plan and verifies a real candidate graph.
- Do not describe CampaignRadius alone as the final idea after the user has selected the combined action layer.
- New in-flight competitor evidence can invalidate earlier crowding and originality assumptions. Re-run the collision gate before treating any winner score as current.

## 2026-08-19: Separate repository scale, dependency scale, and optimizer combinations

- Never present a candidate-combination count without naming it; `2^N` combinations are not repositories or dependencies.
- Always report verified scale with separate counts for repositories, package instances, unique package versions, dependency edges, vulnerable versions, candidate actions, and candidate combinations.
- Do not call exact OSV matching “best-in-field vulnerability detection.” The product can lead in proof-carrying portfolio remediation while relying on authoritative vulnerability sources.

## 2026-08-19: Say proposed fix, not candidate

- “Candidate” is optimizer jargon and obscures the user’s job. In product explanations, say proposed fix: a real PR, commit, or updated lockfile.
- Detection does not require a proposed fix. Fix verification is a second-stage workflow after the baseline exposure result.
- Do not make subset enumeration the product story. Lead with verifying whether real proposed fixes remove selected exposure and whether other risks remain.

## 2026-08-19: Score every downstream phase visibly

- From Forge onward, every pipeline phase must end with an evidence-backed numeric score, deductions, failed hard gates, unverified assumptions, required rework, and winner-readiness estimate.
- Frontend, technology stack, and integrations must be mapped exhaustively before implementation. A component name without ownership, data flow, failure behavior, security boundary, test, and operational consequence is incomplete.
- A high aggregate score cannot override a critical failure such as unsupported claims, decorative HydraDB, fabricated evidence, false-clean output, or a missing core integration.

## 2026-08-19: Keep long quality gates legible

- During an exhaustive audit, report the current phase, what has passed, the exact remaining blocker class, and what comes next; silence makes deliberate fail-closed rework look stuck.
- Stop repeated micro-audits once a phase is structurally green. Batch related repairs, then request one fresh decisive audit against new hashes.
## 2026-08-20 — Deadline language must not imply silent scope reduction

- Saying “shorten product scope” without clearly labeling it as a last-resort contingency sounds like advance permission to lower quality or omit approved features.
- Default deadline strategy: execute the complete forged scope, parallelize independent work, and eliminate rework.
- Any deferral must follow a missed checkpoint, be explicit before action, preserve the winning thesis and demo, and never weaken truth, security, testing, deployment, or submission gates.

## 2026-08-20 — Name the exact pipeline transition

- A continuation handoff must state both the orchestrator and the first dispatched phase; “continue the pipeline” is too ambiguous near a deadline.
- For this project the explicit transition is conductor adoption of completed Intel/Warroom/Forge, then Critique, URL pre-verification, and Build.

## 2026-08-20 — Distinguish name availability from deployment reservation

- A read-only 404 check proves only that a candidate URL currently has no responding project; it does not reserve the name.
- A Vercel project URL cannot serve as HydraCut's compliant production deployment because the approved architecture requires a Linux VM hosting the full Docker Compose stack and private self-hosted HydraDB.
- Record three separate facts: repository namespace ownership, frontend naming candidate, and the DNS hostname actually pointed to the deployment VM.

## 2026-08-20 — Disclose infrastructure cost before recommending a provider

- Never present a paid VM setup as the default without stating the hourly and likely deadline-window cost first.
- Separate free components from paid infrastructure explicitly: repository, SSH, ACME, and wildcard DNS can be free while compute is not.
- If a zero-cost tier cannot satisfy the approved runtime architecture, state that conflict plainly instead of implying a tiny or incompatible free host is equivalent.

## 2026-08-20 — Treat zero-cost deployment as an explicit architecture constraint

- Once the user rejects all paid infrastructure, do not continue presenting billable providers as the default path.
- First validate whether local Docker plus a free HTTPS tunnel can preserve the complete self-hosted service topology and native graph proof.
- Record any deployment-host deviation transparently and keep every product, evidence, privacy, and fail-closed gate intact.

## 2026-08-20 — A public tunnel is not cloud deployment

- Do not equate public reachability with cloud hosting: a tunnel still depends on the user's local machine remaining online.
- When the user requires deployment independent of local hardware, every persistent runtime service must move to remote compute.
- Zero cost and cloud persistence must both be verified before closing the credential checkpoint; neither may be silently traded away.
